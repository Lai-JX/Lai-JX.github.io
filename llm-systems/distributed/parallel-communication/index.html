    大模型并行方式的通信量计算¶

    快速复习¶

    • 先声明统计口径：每 rank 发送量、收发总量、全组聚合量和链路实际流量不是同一个数。
    • 对 \(p\) 个 rank、大小为 \(M\) 的完整张量，ring AllReduce 的每 rank 发送量为 \(2\frac{p-1}{p}M\)；AllGather 或 ReduceScatter 各为 \(\frac{p-1}{p}M\)。
    • DP 通常通信梯度，TP/SP 通信激活，PP 传相邻 stage 的激活/梯度，EP 搬运 routed token，CP 交换 K/V，FSDP/ZeRO-3 聚合参数并分散梯度。
    • 只算字节仍不够：小消息常受启动延迟影响，大消息受带宽与拓扑影响，最终还要看通信能否与计算重叠。

    1. 统一符号与统计口径¶

    本文默认：

    • \(p\)：某个通信组的 rank 数，不一定等于总 GPU 数；
    • \(M\)：一次 collective 对应的完整逻辑张量字节数；
    • \(b\)：每个元素的字节数，例如 BF16/FP16 为 2；
    • “每 rank 通信量”默认指每个 rank 发送的 payload 字节数（TX）；
    • 对称 collective 的每 rank 接收量与发送量相同；若统计 TX+RX，应再乘 2。

    必须区分以下四种口径：

    口径 含义
    每 rank 发送量 单个 rank 注入网络的 payload，最适合估算该 rank 的通信时间
    每 rank 收发量 TX+RX；对称 collective 通常是发送量的 2 倍
    全组聚合发送量 所有 rank 的发送量求和
    链路流量 数据实际经过各条 NVLink、PCIe、IB/RoCE 链路的字节数，受拓扑和路由影响

    下文公式给的是理想化 payload，不包含协议头、对齐、padding、重传、控制消息，也不代表某条物理链路上的精确流量。

    2. Ring collective 的基础公式¶

    NCCL 定义了 AllReduce、AllGather、ReduceScatter、AllToAll 等 collective；其中 ReduceScatter 后接 AllGather 与 AllReduce 等价。操作语义可参考 NCCL Collective Operations，ring 的校正因子也可与 NVIDIA nccl-tests 性能文档 中的 PERFORMANCE.md 对照。在理想 ring 算法下：

    原语 \(M\) 的定义 每 rank 发送量 全组聚合发送量
    AllReduce 每个 rank 输入/输出的完整张量 \(2\frac{p-1}{p}M\) \(2(p-1)M\)
    AllGather gather 后的完整张量；每 rank 初始持有 \(M/p\) \(\frac{p-1}{p}M\) \((p-1)M\)
    ReduceScatter reduce 前的完整张量；每 rank 最终持有 \(M/p\) \(\frac{p-1}{p}M\) \((p-1)M\)
    AllToAll 这里改用每 rank 本地发送缓冲区 \(M_{local}\) \(\frac{p-1}{p}M_{local}\) \((p-1)M_{local}\)
    Point-to-Point 单次消息 发送方 \(M\) \(M\)

    AllReduce 有两轮 ring：ReduceScatter 和 AllGather 各走 \(p-1\) 步，每步发送 \(M/p\)，所以：

    \[ V_{\mathrm{AR,rank}} =2(p-1)\frac{M}{p} =2\frac{p-1}{p}M. \]

    若用简单的 \(\alpha\)-\(\beta\) 模型，ring AllReduce 的时间近似为：

    \[ T_{\mathrm{AR}} \approx 2(p-1)\alpha +2\frac{p-1}{p}\frac{M}{B_{\mathrm{eff}}}, \]

    其中 \(\alpha\) 是每步启动/同步延迟，\(B_{\mathrm{eff}}\) 是有效单向带宽。这个模型解释了为什么 decode 的小 collective 可能“字节不多但仍然很慢”：此时延迟项和同步项占比很高。

    NCCL 会根据消息大小、GPU 拓扑和配置选择 ring、tree、CollNet 等算法。上式适合估算 ring 的逻辑量，不是对所有 NCCL 执行计划的精确预测。

    3. 各种并行方式通信什么¶

    3.1 Data Parallel（DP / DDP）¶

    设每次同步的梯度总大小为 \(G\)，数据并行度为 \(d\)。DDP 使用一次或多次 bucketed AllReduce；忽略 bucket padding 后，每 rank 每个同步步发送：

    \[ V_{\mathrm{DP}} =2\frac{d-1}{d}G. \]

    梯度累积若只在最后一个 microbatch 同步，通信次数按 optimizer step 计算，而不是按 microbatch 计算。纯推理 DP 是多份独立副本，通常没有逐层模型 collective；请求分发和最终结果汇总属于服务系统通信，不应套用梯度公式。

    3.2 Tensor Parallel（TP）与 Sequence Parallel（SP）¶

    设张量并行度为 \(t\)，未切分激活大小为：

    \[ M_{act}=B\times S\times D\times b, \]

    其中 \(B\) 为 microbatch，\(S\) 为本次处理的 token 数，\(D\) 为 hidden size。

    经典 Megatron Transformer 层在 attention 输出和 MLP 输出各有一次 TP AllReduce，因此仅前向、每层、每 rank 的发送量约为：

    \[ V_{\mathrm{TP,fwd/layer}} =2\times 2\frac{t-1}{t}M_{act} =4\frac{t-1}{t}M_{act}. \]

    训练反向还会在对应列并行线性层的输入梯度上发生两次同规模归约，所以前向加反向约为：

    \[ V_{\mathrm{TP,train/layer}} \approx 8\frac{t-1}{t}M_{act}. \]

    开启 Sequence Parallel 后，一个 AllReduce 常被重新组织为一对 ReduceScatter + AllGather。理想 ring 字节量仍为：

    \[ \frac{t-1}{t}M_{act} +\frac{t-1}{t}M_{act} =2\frac{t-1}{t}M_{act}, \]

    所以 SP 的首要收益是让部分激活沿序列维保持分片并改善显存与 overlap，而不是自动把总通信字节减半。Megatron Core 对 TP/SP 的 forward AllGather、backward ReduceScatter 语义有明确说明，见 tensor parallel layers。具体实现若融合 collective、改变布局或使用低精度通信，实际量会变化。

    例子。 TP=8、decode batch=8、\(S=1\)、\(D=8192\)、BF16 时：

    \[ M_{act}=8\times1\times8192\times2=128\ \mathrm{KiB}. \]

    两次 AllReduce 的每 rank 前向发送量为：

    \[ 4\times\frac{7}{8}\times128\ \mathrm{KiB} =448\ \mathrm{KiB/layer}. \]

    若有 80 层，则约为 35 MiB/decode step/rank。虽然字节量不算大，但它被拆成许多逐层、依赖严格的小 collective，延迟和同步可能比纯带宽更关键。

    3.3 Pipeline Parallel（PP）¶

    设 pipeline 有 \(q\) 个 stage，相邻 stage 每个 microbatch 传输的激活为 \(A\) 字节：

    • 推理前向：每个边界传 \(A\)，全 pipeline 聚合发送量为 \((q-1)A\)；
    • 训练：反向还要传同形状的激活梯度，聚合发送量约为 \(2(q-1)A\)；
    • 一个 step 有 \(m\) 个 microbatch 时，再乘 \(m\)。

    PP 是相邻 stage 的 P2P 通信，端点与中间 stage 的发送/接收方向不同，因此用“每个边界的消息量”通常比用平均每 rank 更清楚。实际性能还受 pipeline bubble、1F1B/交错调度以及 P2P 与计算 overlap 影响。Megatron Core 将 PP 的核心通信描述为 stage 间 activation send/receive，见 Parallelism Strategies Guide。

    3.4 Expert Parallel（EP / MoE）¶

    设 EP 组大小为 \(e\)，每个 rank 初始有 \(N\) 个 token，hidden size 为 \(D\)，每 token 路由到 \(k\) 个专家，通信精度每元素 \(b\) 字节。路由后的本地 token payload 为：

    \[ M_{route}=kNDb. \]

    若专家和 token 近似均匀分布，发往其他 rank 的比例约为 \((e-1)/e\)。MoE 前向通常包含 dispatch 与 combine 两次 AllToAll，因此每 rank 发送量近似：

    \[ V_{\mathrm{EP,fwd/layer}} \approx2\frac{e-1}{e}M_{route} =2\frac{e-1}{e}kNDb. \]

    训练反向还要走对应的反向交换，粗略可再乘 2。真实流量必须用每个目的 rank 的 token 数计算，因为以下因素都会偏离均匀假设：

    • 专家负载不均；
    • capacity factor、drop 或 padding；
    • token permutation 的索引/scale 元数据；
    • shared expert、expert TP；
    • FP8/INT8 dispatch 或通信融合。

    因此 EP 最值得同时报告“理论 payload”和“每 rank 实际 routed token / bytes”，否则平均值会掩盖热点 rank。

    3.5 Context Parallel（CP）¶

    设上下文并行度为 \(c\)，一层全序列 K 和 V 的合计 payload 为 \(M_{KV}\)。每个 rank 初始只持有 \(M_{KV}/c\)。标准 ring KV exchange 进行 \(c-1\) 步，因此前向每 rank 发送：

    \[ V_{\mathrm{CP,fwd/layer}} \approx\frac{c-1}{c}M_{KV}. \]

    Megatron Core 的 CP 在 forward 交换完整序列的 KV，在 backward 再次聚合 KV，并对 KV 梯度做 ReduceScatter。若都按同样的 KV payload 估算，训练前向加反向约为：

    \[ V_{\mathrm{CP,train/layer}} \approx3\frac{c-1}{c}M_{KV}. \]

    这是标准实现的数量级公式；causal load balance、分层 CP、AllToAll/Ulysses 路径、MQA/GQA/MLA 都会改变精确 payload。尤其 MQA/GQA/MLA 的 KV 头数或 latent 更小，会直接降低 CP 通信量。实现说明见 Megatron Core Context Parallel。

    3.6 FSDP / ZeRO-3¶

    设一个 FSDP unit 的完整参数为 \(W\) 字节，sharding group 大小为 \(f\)：

    • 参数 AllGather：每 rank 发送 \(\frac{f-1}{f}W\)；
    • 梯度 ReduceScatter：每 rank 发送 \(\frac{f-1}{f}W\)，若梯度通信 dtype 不同，应按实际梯度字节重算。

    若 forward 后立即 reshard，backward 前需要再次 AllGather 参数，则一次训练迭代约为：

    \[ V_{\mathrm{FSDP,reshard}} \approx3\frac{f-1}{f}W \]

    ——forward AllGather、backward AllGather、gradient ReduceScatter 各一次。若保留完整参数直到 backward，则少一次 AllGather，约为：

    \[ V_{\mathrm{FSDP,no\ reshard}} \approx2\frac{f-1}{f}W. \]

    PyTorch 的 FSDP 教程将其描述为 forward 聚合参数、backward ReduceScatter 梯度；forward 后释放完整参数时，backward 还需再次聚合，见 PyTorch FSDP tutorial 与 FSDP API。

    4. 混合并行怎样合计¶

    DP、TP、PP、EP、CP 往往使用不同 process group。不要把各并行度直接相乘后套进一个公式，而应按执行图逐项累加：

    1. 列出每层/每 step 的 collective 或 P2P；
    2. 写清其 process group 大小；
    3. 写清通信前的实际 tensor shape、dtype 和是否 top-k 复制；
    4. 代入对应原语公式；
    5. 乘层数、microbatch 数和执行次数；
    6. 最后再分析哪些通信串行、哪些可以 overlap。

    可以使用如下清单：

    事件 组 原语 shape / dtype 次数 每 rank TX 是否在关键路径
    attention TP 聚合 TP AllReduce 或 RS/AG \(B\times S\times D\) / BF16 每层 1 次 代入公式 是/可部分 overlap
    MLP TP 聚合 TP AllReduce 或 RS/AG \(B\times S\times D\) / BF16 每层 1 次 代入公式 是/可部分 overlap
    MoE dispatch/combine EP AllToAll routed tokens / 实际通信 dtype 每 MoE 层 2 次 按 route 统计 通常是
    stage 交接 PP P2P activation / 实际 dtype 每 microbatch \(A\) 取决于调度
    梯度同步 DP/FSDP AR 或 RS gradient bucket / reduce dtype 每同步步 代入公式 可与 backward overlap

    5. 从通信量到通信时间¶

    通信量只是第一步。真实性能还取决于：

    • 消息大小：小消息由 latency 主导，大消息才接近链路带宽；
    • collective 数量：相同总字节拆成几十个同步点通常更慢；
    • 拓扑：NVLink/NVSwitch、PCIe、跨节点 IB/RoCE 的带宽与跳数不同；
    • 算法：ring、tree、hierarchical、CollNet 的 step 数和链路利用不同；
    • 竞争：TP、EP、CP 或 P/D 传输可能争用同一 NIC/NVLink；
    • 重叠：通信若完全被独立计算覆盖，未必进入端到端关键路径；
    • 不均衡：collective 的完成时间由最慢 rank 决定。

    验证时至少同时记录：collective 名称、tensor bytes、持续时间、算法/协议、各 rank 起止时间、NVLink/PCIe/NIC 吞吐，以及端到端 throughput/latency。
