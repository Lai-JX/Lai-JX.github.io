    PyTorch CUDA 显存管理机制¶

    快速复习¶

    • 张量释放后，显存通常先回到 PyTorch caching allocator，而不是立刻还给 CUDA 驱动。
    • allocated 表示活跃张量占用，reserved 表示 allocator 管理的显存；nvidia-smi 还包含 CUDA context、NCCL 等开销。
    • empty_cache() 不能释放活跃张量，也不是常规的 OOM 修复手段。
    • allocated 持续上涨先查引用和计算图；reserved - allocated 很大再查碎片。
    • 跨 stream 正确性同时需要处理执行依赖和张量生命周期。

    1. 先建立正确的分层模型¶

    PyTorch uses a caching memory allocator to speed up memory allocations. This allows fast memory deallocation without device synchronizations. However, the unused memory managed by the allocator will still show as if used in nvidia-smi. You can use memory_allocated() and max_memory_allocated() to monitor memory occupied by tensors, and use memory_reserved() and max_memory_reserved() to monitor the total amount of memory managed by the caching allocator. Calling empty_cache() releases all unused cached memory from PyTorch so that those can be used by other GPU applications. However, the occupied GPU memory by tensors will not be freed so it can not increase the amount of GPU memory available for PyTorch.

    一次 CUDA 张量分配涉及三层：

    Python 对象 / autograd 引用
          ↓ 决定张量是否仍然存活
Tensor Storage
          ↓ 向 PyTorch 分配器申请 block
CUDACachingAllocator
          ↓ 必要时才向 CUDA 驱动申请 segment
CUDA Driver / GPU 显存

    因此“Python 变量被删除”“显存可被 PyTorch 复用”“显存已归还 CUDA 驱动”是三件不同的事：

    • memory_allocated()：当前存活张量占用的显存；
    • memory_reserved()：PyTorch 缓存分配器管理的总显存，包含已分配 block 和可复用空闲 block；
    • nvidia-smi：从驱动视角观察进程占用，还可能包含 CUDA context、NCCL 和其他绕过 PyTorch 分配器的内存。

    通常可以近似理解为：allocated <= reserved <= 进程在驱动侧的占用。最后一个不等式不是 allocator 的严格统计恒等式，而是说明驱动侧往往还有 PyTorch 无法归类的占用。官方的 CUDA memory management 明确区分了 allocated 和 reserved。

    2. 张量什么时候真正失去占用¶

    在 CPython 中，Tensor 对象主要依赖引用计数管理；多个 Tensor view 还可能共享同一块 Storage。只有相关引用和异步使用都结束后，allocator 才能安全复用对应 block。常见的隐式引用包括：

    • autograd 为反向传播保存的激活；
    • 把带计算图的 loss 或输出直接放入列表；
    • 闭包、异常栈或 Python 引用环；
    • 梯度张量仍由参数的 .grad 持有。

    训练时的主要常驻项可粗略拆成参数、梯度、优化器状态和为 backward 保存的激活。不要把所有峰值都归因于 allocator；先确认究竟是哪类张量仍然活着。

    # 统计指标时切断计算图
loss_history.append(loss.detach().cpu().item())

# set_to_none=True 不保留原梯度 buffer，通常比填零更省显存
optimizer.zero_grad(set_to_none=True)

    如果存在 Python 引用环，张量可能要等循环垃圾回收才释放，显存曲线会呈现逐步上涨后突然下降。PyTorch 的 GPU memory reference-cycle 分析 展示了这种典型模式。

    3. 为什么需要 caching allocator¶

    直接频繁调用 cudaMalloc/cudaFree 成本较高，而且释放可能引入设备同步。PyTorch 默认使用缓存分配器：

    1. 没有合适空闲 block 时，向 CUDA 申请较大的 segment；
    2. 从 segment 中切分 block 满足张量申请；
    3. 张量释放后，block 先回到 PyTorch 的空闲池；
    4. 后续兼容的申请直接复用 block，避免再次进入 CUDA 驱动；
    5. 相邻空闲 block 在条件允许时合并。

    分配器还要保证跨 stream 使用的安全性。执行依赖与内存生命周期是两个不同问题：wait_stream() 确保 side stream 在数据生产完成后再读取，record_stream() 确保 allocator 在 side stream 使用结束前不复用 Storage。

    s = torch.cuda.Stream()
x = torch.randn(1024, device="cuda")  # 在默认 stream 上初始化

s.wait_stream(torch.cuda.default_stream(x.device))
with torch.cuda.stream(s):
    y = x * 2
x.record_stream(s)

    省略 wait_stream() 可能在 x 尚未初始化完时就开始读取；省略 record_stream() 则可能在 Python 侧释放 x 后过早复用它的 Storage。更完整的说明见官方 CUDA stream semantics。

    4. empty_cache() 到底做什么¶

    torch.cuda.empty_cache() 只会把完全空闲的缓存 segment 归还给 CUDA：

    • 不会释放仍由张量占用的显存；
    • 一般不会增加当前 PyTorch 进程自己可用的显存，因为空闲 block 本来就能复用；
    • 能降低 nvidia-smi 中的进程占用，并让其他进程使用这些 segment；
    • 某些碎片化场景下可能有帮助，但不应放在每一步训练中当作常规优化。

    频繁清空缓存会破坏复用，并重新引入昂贵的驱动分配。官方 empty_cache() 文档 也强调它不能增加 PyTorch 可用显存。

    5. 碎片化为何会导致 OOM¶

    假设 reserved 中还有 1 GiB 空闲，但它分散在多个无法合并的小 block 中，此时申请一块连续 800 MiB 显存仍可能失败。这就是“总空闲量足够，但没有合适连续块”的外部碎片。

    容易诱发碎片的负载包括：

    • batch size、序列长度频繁变化；
    • 大小相近但不完全相同的临时张量交替出现；
    • 部分长期存活 block 把 segment 切割开；
    • 多 stream 下 block 尚未满足安全复用条件。

    当前官方文档推荐的环境变量名是 PYTORCH_ALLOC_CONF，旧名 PYTORCH_CUDA_ALLOC_CONF 是兼容别名。应在启动 Python 进程前设置，常用选项包括：

    $env:PYTORCH_ALLOC_CONF = "backend:native,expandable_segments:True"
    选项 用途 注意
    backend:native 使用 PyTorch 原生分配器 默认后端
    backend:cudaMallocAsync 使用 CUDA 异步分配器 需要 CUDA 11.4+，部分 native 统计项不再有意义
    expandable_segments:True segment 可按需扩展 适合 batch/序列长度变化，仍属实验选项
    max_split_size_mb 限制大 block 被切分 仅建议在确认大量 inactive split block 后作为最后手段
    garbage_collection_threshold 达到容量阈值后主动回收旧空闲 block 主要用于延迟敏感服务，仅 native 有效

    max_split_size_mb、garbage_collection_threshold 等配置依赖 backend:native；使用 cudaMallocAsync 后，一部分原生 allocator 统计项和选项不再有意义。完整语义以当前 PyTorch 版本的 allocator 配置文档 为准。

    6. 可复用的显存诊断代码¶

    import torch

MiB = 1024 ** 2

def show_cuda_memory(tag: str = "") -> None:
    torch.cuda.synchronize()
    print(
        tag,
        f"allocated={torch.cuda.memory_allocated() / MiB:.1f} MiB",
        f"reserved={torch.cuda.memory_reserved() / MiB:.1f} MiB",
        f"peak_allocated={torch.cuda.max_memory_allocated() / MiB:.1f} MiB",
        f"peak_reserved={torch.cuda.max_memory_reserved() / MiB:.1f} MiB",
    )

torch.cuda.reset_peak_memory_stats()
# run_workload()
show_cuda_memory("after workload")
print(torch.cuda.memory_summary(abbreviated=True))

    定位复杂 OOM 时，记录 allocator 历史并生成快照：

    torch.cuda.memory._record_memory_history(max_entries=100_000)
try:
    run_workload()
finally:
    torch.cuda.memory._dump_snapshot("cuda-memory.pickle")

    将文件拖入 PyTorch Memory Visualizer 可查看 active memory timeline、segment/block 状态及 OOM 时刻。上述带下划线的历史记录接口属于内部 API，版本升级时应重新核对签名。

    快照只看得到 PyTorch allocator 管理的内存，看不到 NCCL 等直接 CUDA 分配；可用 torch.cuda.device_memory_used() 与 allocator 统计的差值辅助判断。详见官方 Understanding CUDA Memory Usage。

    7. OOM 排查顺序¶

    1. 记录峰值 max_memory_allocated()，确认是否确实接近物理容量。
    2. 若 allocated 持续上升，优先查存活引用和意外保留的计算图。
    3. 若 reserved - allocated 很大，查看 memory_summary() 和 snapshot 中的 inactive split blocks。
    4. 若驱动占用明显大于 reserved，检查 NCCL、自定义 CUDA 扩展及其他库。
    5. 再采用减小 batch/序列长度、混合精度、activation checkpointing、分片优化器等算法级手段。
    6. 只有证据指向 allocator 碎片时，才调整 PYTORCH_ALLOC_CONF。

    核心原则是：先判断“活跃张量过多”还是“空闲显存无法复用”，两者的解决方案完全不同。

    现象 更可能的原因 下一步
    allocated 逐步增长 引用未释放、意外保留 autograd graph 查看 active timeline 和分配栈
    allocated 正常，reserved 明显更高 缓存或碎片 查看 inactive split blocks
    nvidia-smi 明显高于 reserved CUDA context、NCCL 或其他库直接分配 对比 device_memory_used()
    峰值只在 forward 后段出现 saved activations 较多 混合精度、checkpointing、缩短序列
    峰值只在首次执行出现 初始化、autotune 或临时 workspace 区分冷启动峰值与稳态峰值
