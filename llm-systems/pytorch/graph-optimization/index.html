    PyTorch 计算图优化¶

    快速复习¶

    • PyTorch 中的 autograd graph、FX/Inductor graph 和 CUDA Graph 解决的是不同问题。
    • 图优化的主要收益往往来自减少 kernel launch 和全局显存读写，而不只是减少 FLOPs。
    • 融合受数据依赖、迭代域、资源占用、mutation/alias 和图边界约束，并非越大越好。
    • 静态 shape 便于特化，动态 shape 便于复用；实际系统常用 bucketing 折中。
    • 最终判断标准是端到端稳态性能，不能只看节点数或生成 kernel 数。

    1. 图优化的本质¶

    图优化不是单纯“减少算子数量”，而是在保持程序语义的条件下，降低关键路径上的成本：

    总时间 ≈ Python/dispatcher 开销
       + kernel launch 开销
       + 显存读写时间
       + 实际计算时间
       + 同步与通信时间

    对许多逐元素算子，计算量很小，主要成本是反复读写显存和启动 kernel。因此把多个算子放进一个 kernel，往往比减少几次标量运算重要得多。

    先区分三个经常混用的“图”：

    图 记录什么 主要用途
    autograd graph Tensor 操作对应的梯度依赖 反向传播
    FX/ATen/Inductor graph 可分析、可变换的算子与数据依赖 编译、融合和代码生成
    CUDA Graph 一段已经确定的 GPU 工作及依赖 低开销重复提交

    它们可以衔接使用，但不是同一种表示。

    2. FX 图是什么¶

    FX 使用 GraphModule 表示 Python 可调用对象和一张有序、无环的节点图。常见节点类型包括：

    • placeholder：函数输入；
    • get_attr：读取参数或常量属性；
    • call_function、call_method、call_module：执行操作；
    • output：返回值。

    简单观察：

    import torch
from torch import nn
from torch.fx import symbolic_trace

class Block(nn.Module):
    def forward(self, x, bias):
        return torch.relu(x + bias)

gm = symbolic_trace(Block())
print(gm.graph)
print(gm.code)

    FX 是可变换 IR，但 torch.compile 内部得到的图和传统 symbolic_trace 并不完全等价；前者来自 Dynamo/AOTAutograd，并配合 FakeTensor、shape/stride、Guards 和 autograd 等编译信息。symbolic_trace 也无法直接追踪所有依赖 Tensor 数据的 Python 控制流。

    手写 FX pass 时，修改完图应执行 graph.lint() 检查拓扑和引用，再执行 GraphModule.recompile() 让 Python forward 与图同步。参考官方 torch.fx 文档。

    3. 编译链路中的主要优化¶

    3.1 规范化、函数化与分解¶

    高层 PyTorch 操作形式多样，还包含 inplace、view 和别名语义。AOTAutograd/AOTDispatcher 先把它们转换成更规则的表示，再将复合算子分解为后端理解的核心算子。这样做不是直接提速，而是让后续依赖分析、融合和代码生成更可靠。

    一些经典图变换也属于这个层次，例如在语义允许时折叠常量表达式、移除无副作用且结果未被使用的节点，以及合并冗余转换。具体是否执行取决于当前 backend 和 IR；不能假设所有数学上等价的改写都安全，因为浮点精度、随机数、mutation 和 alias 都会限制变换。

    3.2 算子融合¶

    考虑：

    y = torch.relu(x * scale + bias)

    eager 可能依次产生乘法、加法、ReLU kernel，并为中间结果读写全局显存。融合后可在一个 kernel 中完成：

    Eager: read x → write t1 → read t1 → write t2 → read t2 → write y
Fused: read x,bias,scale ────────────────────────────────→ write y

    常见融合类别：

    • 纵向融合：producer 与 consumer 融合，如 pointwise 链；
    • epilogue 融合：把 bias、激活等融合到 matmul/conv 模板尾部；
    • pointwise + reduction 融合：在依赖、资源和调度允许时减少中间读写；
    • 横向融合：无直接依赖但迭代域兼容的操作共同调度，以减少 launch。

    融合并非越多越好。过度融合可能增加寄存器压力、降低 occupancy，或让不同调度需求的算子互相牵制。Inductor 的 scheduler 会基于依赖关系和代价模型选择，而不是把相邻节点无条件拼接。PyTorch 2 论文对 Inductor 的融合与 Triton codegen 有更完整描述。

    判断两个节点能否融合，至少要考虑：

    • producer/consumer 的数据依赖是否允许重排；
    • iteration domain 和索引关系是否兼容；
    • inplace、view、alias 或副作用会不会改变可见语义；
    • 融合后的寄存器、shared memory 和并行度是否仍然合理；
    • 中间结果是否被图外或多个不兼容的 consumer 使用。

    3.3 布局与循环级优化¶

    Tensor 的 shape 相同并不代表访存方式相同，stride/layout 会影响合并访存、向量化及是否需要复制。编译器能利用整张子图的信息：

    • 选择循环顺序和 tile；
    • 尽量让 producer 直接以 consumer 需要的方式产生数据；
    • 消除只为格式转换产生的中间 materialization；
    • 对特定 shape 选择 matmul/conv 实现或 autotune 配置。

    因此不能只看 FX 节点数判断优化质量，还要看生成 kernel、内存流量和实际设备指标。

    3.4 消除中间张量与内存规划¶

    融合可以让中间值停留在寄存器或片上存储，不再形成完整 CUDA tensor。对必须 materialize 的值，编译器还可依据生命周期安排 buffer 复用。

    训练图的显存还有另一层权衡：AOTAutograd partitioner 决定 forward 为 backward 保存哪些值、哪些值在 backward 重算。少保存能降低激活显存，但增加计算量，这与 activation checkpointing 的思想相近。

    3.5 优化层次与收益来源¶

    优化 主要减少 更容易受益的负载
    捕获更大的连续图 Python 往返与优化边界 小算子密集、Python 调度明显
    pointwise/reduction 融合 kernel launch、全局显存流量 memory-bound 算子链
    epilogue 融合 中间张量读写 Linear/Conv 后接 bias、激活
    布局与 tile 选择 非合并访存、低效计算 shape 稳定的 GEMM/Conv/Reduction
    buffer 复用与重计算 峰值显存 训练、长序列或大激活模型
    CUDA Graph replay CPU 提交和 launch 间隙 shape 和地址稳定的小 batch 推理

    4. 图边界决定优化上限¶

    def f(x):
    a = x.sin()
    print(a.shape)  # 可能形成 graph break
    return a.cos()

    若 sin 和 cos 分属两个 graph，编译器无法跨 break 融合，也无法统一规划中间 buffer。优化图之前，通常应先用 TORCH_LOGS=graph_breaks 确认图是否被意外切碎。

    但 fullgraph=True 不是生产环境必须项。某段不频繁执行或天然不适合捕获的 Python 逻辑保留 eager，可能比为消除一个 break 大幅改写代码更合理。

    5. 静态特化与动态形状¶

    已知具体 shape/stride 时，编译器可以生成高度特化的 tile、向量宽度和 kernel；动态 shape 则提高复用范围，减少输入变化带来的编译次数。

    策略 优点 风险
    静态特化 优化空间大，稳态 kernel 可能更快 shape 多时产生编译风暴和缓存膨胀
    符号动态 一份产物覆盖多个尺寸 Guard 更复杂，部分优化受限，仍可能被迫特化
    padding/bucketing 兼顾稳定 shape 和输入变化 多做无效计算、可能增加显存

    LLM serving 中常用长度分桶，实质是减少 shape 种类，让编译缓存和高效 kernel 更容易复用。

    6. CUDA Graphs 与“计算图编译”不是一回事¶

    两者容易混淆：

    • Dynamo/FX/Inductor graph：编译器 IR，用于分析语义、融合和生成代码；
    • CUDA Graph：记录一串已经确定的 GPU 工作，并以较低 CPU launch 开销重放。

    CUDA Graph replay 要求每次重放时 kernel 参数和内存地址保持有效，因此通常配合固定输入 buffer 与图私有内存池。mode="reduce-overhead" 会在适用时使用 CUDA Graphs，但可能因缓存 workspace 增加显存，也会受输入 mutation、动态形状等条件限制。以当前版本 torch.compile mode 文档 为准。

    7. 如何判断优化是否真的有效¶

    建议依次回答：

    1. 图捕获是否完整？ 看 Graph Break。
    2. 产物是否稳定复用？ 看 Guard failure 和 Recompile。
    3. kernel 是否减少？ 用 PyTorch Profiler / Nsight Systems 比较 launch 数量。
    4. 显存流量是否下降？ 看 kernel 时间、带宽指标和中间 allocation。
    5. 峰值显存是否变化？ 比较 max_memory_allocated()，注意 CUDA Graph workspace/private pool。
    6. 端到端是否更快？ 排除编译和 warm-up，用真实 shape 分布测量稳态吞吐与尾延迟。
    $env:TORCH_LOGS = "graph_breaks,recompiles,perf_hints,output_code"
python benchmark.py

    日志很多时，可按阶段逐个打开。output_code 能查看 Inductor 生成代码；perf_hints 能解释 CUDA Graphs 等优化为何没有应用。官方 编译器故障排查指南 还提供 TORCH_TRACE/tlparse 的全局分析方法。

    8. 一组实用判断¶

    • Graph Break 少，不等于一定快；还要看图内是否有可融合的小算子。
    • kernel 数少，不等于一定快；大融合 kernel 可能受寄存器或并行度限制。
    • 编译后显存增加，不等于泄漏；可能来自编译缓存、autotune 或 CUDA Graph 私有池。
    • 动态 shape 少重编译，不等于一定比静态快；应以真实输入分布衡量总成本。
    • torch.compile 优化的是被捕获区域；数据加载、分布式通信和 Python 侧调度仍需分别分析。
