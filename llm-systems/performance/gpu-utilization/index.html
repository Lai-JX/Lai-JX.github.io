    GPU 利用率：指标、口径与排查方法¶

    快速复习¶

    • nvidia-smi 的 GPU-Util 主要回答“采样窗口内有没有 kernel 在运行”，不能直接表示 Tensor Core 或全部 SM 已经跑满。
    • Memory-Util 是显存读写活动时间占比，不是显存容量占用率，也不等同于达到峰值带宽的百分比。
    • SM Active、occupancy、Tensor pipe active、DRAM throughput 分别描述不同资源，不能互相替代。
    • 训练/推理是否有效利用 GPU，最终仍要和 tokens/s、TTFT、TPOT、有效 FLOPs 等业务指标一起判断。
    • 推荐按“业务指标 → 设备遥测 → 时间线 → 单 kernel”逐层下钻，而不是只盯着一个百分比。

    1. “GPU 利用率”至少有四种口径¶

    日常讨论中的“利用率”可能指完全不同的量：

    1. 时间利用率：采样期间 GPU 是否有工作；
    2. 并行度/驻留度：多少 SM、warp 能同时驻留；
    3. 资源吞吐率：计算管线或显存带宽达到了峰值的多少；
    4. 有效工作效率：真正完成了多少模型计算或业务请求。

    因此，看到“GPU 利用率 100%”只能先说明 GPU 很忙，不能立即推出“GPU 算力已经跑满”。一个持续运行、但并行度很低或大部分时间等待显存的 kernel，同样可以让粗粒度 busy 指标接近 100%。

    2. 常用指标及正确含义¶

    层次 常见指标 回答的问题 容易误读的地方
    设备 busy nvidia-smi GPU-Util / NVML utilization.gpu 采样窗口内，有 kernel 执行的时间占比 只要有 kernel 在执行就算 busy，不代表所有 SM 或计算管线饱和
    显存活动 Memory-Util / NVML utilization.memory 采样窗口内，全局显存发生读写的时间占比 不是 memory.used / memory.total，也不是峰值带宽利用率
    显存容量 memory.used、memory.total 分配/保留了多少显存容量 容量高不等于带宽高；缓存分配器还会让已用容量高于活跃张量容量
    SM 活跃 DCGM_FI_PROF_SM_ACTIVE 每个 SM 至少有一个 active warp 的时间比例，再对 SM 求平均 active warp 可能正在等待访存，并不一定在发射算术指令
    SM occupancy DCGM_FI_PROF_SM_OCCUPANCY、Achieved Occupancy 驻留 warp 数相对硬件上限的比例 occupancy 高不保证快；计算受限 kernel 达到所需并行度后，再提高 occupancy 可能无收益
    计算管线 PIPE_TENSOR_ACTIVE、FP16/FP32 pipe active Tensor Core 或对应算术管线有多忙 活跃周期比例不等于模型有效 FLOPs，也受数据类型和指令组合影响
    显存吞吐 DRAM_ACTIVE、Nsight Compute DRAM throughput 显存接口是否活跃，以及吞吐接近峰值的程度 DCGM activity 和 Nsight 的 % of peak 不是同一口径
    互联 PCIe/NVLink TX/RX bytes、带宽 是否有大量主机传输或跨卡通信 链路总流量还要结合通信时间、拓扑与 overlap 判断
    频率与功耗 SM clock、power、temperature、throttle reason 性能是否被功耗、温度或时钟限制 低功耗也可能只是 workload 没有喂满 GPU
    应用层 tokens/s、samples/s、TTFT、TPOT/ITL、MFU 用户实际得到多少吞吐和延迟 不同 batch、序列长度、精度和 SLA 下不可直接横比

    NVML 对 GPU-Util 的定义是采样期间一个或多个 kernel 正在执行的时间比例，对 Memory-Util 的定义是全局显存发生读写的时间比例；采样窗口依产品而异。精确定义可查 NVML nvmlUtilization_t。

    DCGM 的 profiling 指标是时间区间上的硬件计数器平均值。官方文档特别说明：SM_ACTIVE 高只是有效利用 GPU 的必要条件之一，SM_OCCUPANCY 高也不必然带来更高性能。字段定义与采集方法见 NVIDIA DCGM Profiling。

    3. MFU：把模型吞吐换算成峰值算力比例¶

    Model FLOPs Utilization（MFU）常写为：

    \[ \mathrm{MFU} =\frac{F_{\text{model/token}}\times R_{\text{token}}} {N_{\text{GPU}}\times P_{\text{peak}}}, \]

    其中：

    • \(F_{\text{model/token}}\)：按某套模型公式估算的每 token FLOPs；
    • \(R_{\text{token}}\)：全局 token 吞吐，单位为 token/s；
    • \(N_{\text{GPU}}\)：GPU 数量；
    • \(P_{\text{peak}}\)：与实际精度、稠密/稀疏模式相匹配的单卡理论峰值 FLOPs/s。

    MFU 比 GPU-Util 更接近“有多少理论计算能力变成了模型有效计算”，但它不是硬件计数器。使用时必须公开以下口径：

    • FLOPs 是否包含 attention、MoE 路由、embedding、loss 与重计算；
    • 分母使用 BF16、FP16、FP8 还是稀疏 Tensor Core 峰值；
    • token/s 是输入、输出还是训练 token，是否包含 padding；
    • 是否包含数据加载、评估、checkpoint 和跨步空闲时间。

    若这些口径不一致，不同报告的 MFU 不能直接比较。算出超过 100% 通常意味着 FLOPs 模型或峰值分母选错，而不是 GPU 超过了物理峰值。

    对于在线推理，MFU 也不能取代延迟指标。大 batch 可以提高 MFU 和总吞吐，却可能恶化 TTFT 或 TPOT，因此至少要同时报告吞吐、TTFT、TPOT/ITL、并发数、输入/输出长度分布和精度。

    4. 如何判断瓶颈¶

    现象 更可能的原因 下一步证据
    GPU-Util 低，时间线上有明显空洞 CPU 调度、数据加载、同步、kernel launch 或请求不足 Nsight Systems 查看 CPU、CUDA API、kernel 与 NCCL 时间线
    GPU-Util 高，但 SM/Tensor/DRAM 吞吐都低 小 kernel、依赖链、分支发散、访存延迟或采样口径过粗 Nsight Compute 查看单 kernel 的 launch、scheduler、warp stall
    SM/Tensor throughput 高，DRAM 相对低 计算受限 检查 Tensor Core 精度、矩阵形状、融合和理论 FLOPs
    DRAM throughput 高，计算吞吐相对低 显存带宽受限 提高算术强度、融合算子、减少中间张量和 KV Cache 流量
    NVLink/PCIe 流量高，GPU 出现同步空洞 通信受限或 overlap 不足 NCCL 时间线、各 rank 流量、拓扑、collective 大小与持续时间
    平均指标尚可，但不同 rank 差异很大 负载不均或 straggler 按 rank 记录 tokens、专家负载、通信与 kernel 时间
    高温、低时钟或 throttle 功耗/散热限制 频率、功耗上限、温度与 throttle reason

    判断 compute-bound 还是 memory-bound 时，应比较计算吞吐和内存吞吐相对各自峰值的比例，并结合算术强度。Nsight Compute 的 Speed of Light 与 Roofline 分析正是为此设计；指标后缀 .pct_of_peak_sustained_elapsed 表示相对持续峰值的比例，详见 Nsight Compute Profiling Guide。

    5. 推荐的测量顺序¶

    5.1 先固定实验条件¶

    • 预热到编译、autotune、CUDA Graph capture 和缓存初始化完成；
    • 固定 batch、输入/输出长度、精度、并行配置和并发；
    • 使用足够长的稳态窗口，避免 1 秒采样把短时 burst 平滑掉；
    • 多次重复并报告分位数，不只记录一次平均值。

    5.2 设备级粗筛¶

    nvidia-smi --query-gpu=timestamp,index,utilization.gpu,utilization.memory,memory.used,memory.total,power.draw,clocks.sm --format=csv -l 1

    这一步适合发现空闲、显存不足、降频和卡间不均衡，但不足以给 kernel 归因。

    服务器长期监控可用 DCGM。先检查目标 GPU 支持的 profiling 字段，再采集需要的指标：

    dcgmi profile --list --entity-id gpu:0
dcgmi dmon --entity-id gpu:0 --field-id 1002,1004,1005 --delay 1000

    字段 1002/1004/1005 分别对应 SM、Tensor pipe 和 DRAM 活跃度。不同 GPU、驱动和 DCGM 版本支持的字段可能不同，应以第一条命令的实际输出为准。

    5.3 时间线定位¶

    用 Nsight Systems 或 PyTorch Profiler 回答：

    • CPU 是否及时提交工作；
    • kernel 之间是否有空洞；
    • memcpy、NCCL 与计算是否 overlap；
    • 哪些阶段占据端到端延迟。

    5.4 单 kernel 下钻¶

    仅对热点 kernel 使用 Nsight Compute，检查：

    • SM 与 DRAM 的 % of peak sustained；
    • achieved occupancy 与寄存器/共享内存限制；
    • warp stall 原因；
    • 内存访问合并、cache hit 和算术强度。

    单 kernel profiler 开销较高，不适合直接代替端到端测量。正确顺序通常是先用时间线找到热点，再缩小采样范围。

    6. 一份最小报告模板¶

    为了让结果可复现，至少记录：

    GPU / driver / CUDA:
模型、精度、量化方式:
并行配置（DP/TP/PP/EP/CP）:
batch、并发、输入/输出长度:
预热与测量时长:

业务：tokens/s，TTFT p50/p99，TPOT p50/p99
设备：GPU-Util，显存 used/total，功耗与时钟
硬件：SM Active，Tensor Active，DRAM throughput，NVLink/PCIe bytes
时间线：compute / communication / idle 占比
MFU：公式、FLOPs 口径与峰值分母

    核心原则是：先用业务指标定义“快”，再用硬件指标解释“为什么快或慢”。
