    vLLM KV Cache 布局与 P/D 传输分析¶

    本文基于本地 vLLM V1 源码，分析 KV Cache 的物理布局、异构 Tensor Parallel 条件下的显存分片，以及 Prefill/Decode 分离部署中的跨节点传输路径和网络瓶颈。

    结论先说：这份本地 vLLM V1 代码已经统一成逻辑 [L,B,H,N,C]，共有 6 种物理 layout。对普通 MHA/GQA 的异构 TP，真正适合零拷贝 head 重分片的是 LBHNC 和 BLHNC；P/D 的主要瓶颈通常不是 KV 容量，而是：

    1. 较小 TP 一侧的 GPU–NIC 路径被聚合；
    2. layer × block 数量导致 RDMA descriptor/posting 开销；
    3. MLA 的 TP 复制放大网络流量或形成固定源 rank 热点；
    4. Decode 必须等待所有 worker 完成，最慢 rank 直接进入 TTFT 关键路径。

    以下分析基于 vLLM 源码提交 5d09eb2cf310486c03385dd8d97aac5ceee5abc1，文中的源码链接固定到该提交。

    1. 当前 KV cache 的组织方式¶

    统一逻辑轴为：

    • L：KV cache layer
    • B：物理 page/block
    • H：本 rank 的 KV head slot
    • N：block 内 token/state
    • C：每个 state 的内容

    注意当前标准视图是每层 [B,H,N,C]，不是传统的 [2,B,...]。普通 attention 的 K、V 被拼在 C 维中：

    C_bytes = (head_size_k + head_size_v) × dtype_bytes
page_bytes = H × N × C_bytes

    MLA 没有独立 V，head_size_v=0。相关定义见 kv_cache_interface.py。

    底层只分配一块连续 int8 backing buffer，然后用 torch.as_strided 为各层建立不同 stride 的视图；多个 HMA cache group 可以覆盖同一块 backing，因为一个 block ID 同时只属于一个 group。地址公式是：

    addr(layer=l, block=b)
  = raw_base + offset + l × layer_stride + b × block_stride

    见 worker/utils.py 和 kv_cache_interface.py。

    2. 六种物理 layout¶

    枚举定义在 kv_cache_layout.py。

    Layout 物理顺序，左慢右快 单层连续 单层 page 连续 可连续切 KV head 跨层 block-major
    LBHNC [L,B,H,N,C] 是 是 是 否
    LBNHC [L,B,N,H,C] 是 是 否 否
    LHBNC [L,H,B,N,C] 是 否 否 否
    BLHNC [B,L,H,N,C] 否 是 是 是
    BLNHC [B,L,N,H,C] 否 是 否 是
    BHLNC [B,H,L,N,C] 否 否 否 是

    旧名称兼容关系：

    HND -> LBHNC
NHD -> LBNHC

    LBHNC¶

    最适合普通 MHA/GQA 的异构 TP。

    一个 head 对应完整连续 [N,C] 区间，因此可以通过：

    head_slice_addr = block_addr + head_offset × N × C_bytes

    直接发起 RDMA，不需要先做 GPU gather/permute。NIXL 和 Mooncake在非 MLA 模型中都会优先请求该 layout，见 NIXL connector.py 和 Mooncake connector.py。

    LBNHC¶

    token-major，旧称 NHD。整页连续，但某个 head 的不同 token 被其他 heads 穿插，无法用一个连续 RDMA region 做 head split。

    NIXL 异构 TP 默认会拒绝该 layout；实验路径可以先传 LBHNC，再在 D GPU 上 permute 成 LBNHC，但会增加额外显存读写，而且 HMA 不支持该后处理，见 base_worker.py。

    BLHNC¶

    同时具备：

    • block 内 [L,H,N,C] 跨层连续；
    • 每层 page 连续；
    • head slice 连续。

    理论上是 P/D 传输最有潜力的 layout。但当前代码里存在两个限制：

    • manager block 被拆成更小 kernel block 时，block_stride 包含其他层，不能再视为一张 dense page，会被显式拒绝，见 kv_cache_interface.py。
    • 对普通 attention，NIXL 当前仍注册每层一个 region；单测明确期望 BLHNC 下三层仍有三个 base address。只有 packed MLA 路径会真正折叠成“一个 block 一个跨层 region”，见 test_nixl_connector.py 和 test_nixl_connector.py。

    所以：BLHNC 提供了物理连续性，但在当前普通 MHA/GQA NIXL 路径中，不等价于 descriptor 数自动从 L×blocks 降为 blocks。

    3. TP 下的单卡显存布局¶

    设：

    • 模型总 KV heads 为 K
    • TP 大小为 T
    • block size 为 S
    • 层数为 L
    • K/V head dim 分别为 Dk/Dv
    • KV dtype 字节数为 e

    普通 MHA/GQA 每卡 KV head 数：

    Hrank(T) = max(1, K / T)

    源码见 model.py。

    于是每层每卡 page：

    Page_rank = S × Hrank(T) × (Dk + Dv) × e

    当 T <= K 时，KV heads 正常分片；当 T > K 时，每卡至少保留一个 head，KV 开始复制。因此整个 TP group 的 KV 容量为：

    KV_total(T) ∝ max(K, T)

    MLA 则始终是：

    Hrank = 1
Page_rank = S × latent_dim × e

    其 latent KV 在 TP ranks 间复制。

    4. P/D 跨节点传输路径¶

    以 NIXL pull 为例：

    Proxy
  ├─请求 P
  │   └─P 完成 prefill，返回 engine、block IDs、rank/地址元数据
  └─请求 D
      └─D scheduler 分配本地 blocks
          └─WAITING_FOR_REMOTE_KVS
              └─ZMQ/side channel 握手
                  └─交换 TP/PP、base_addr、stride、layout、block_len
                      └─NIXL RDMA READ
                          P GPU VRAM
                          -> PCIe/NVLink
                          -> P NIC
                          -> IB/RoCE
                          -> D NIC
                          -> PCIe/NVLink
                          -> D GPU VRAM
                              └─所有 D workers 完成
                                  └─下一次 scheduler step 开始 decode

    真正数据传输是异步 NIXL READ，见 pull_worker.py。

    D 请求在传输期间处于 WAITING_FOR_REMOTE_KVS，收到完成信号后才恢复调度，见 scheduler.py 和 scheduler.py。

    所有 worker 的 finished_recving 会被聚合计数，因此整体完成时间是：

    T_transfer_barrier = max(T_rank0, T_rank1, ... T_rankN)

    见 kv_connector/utils.py。

    5. 异构 TP 的 rank 映射¶

    以下把 P 视为远端 producer，D 视为本地 consumer。

    条件 数据路径 主要风险
    P_TP = D_TP D_i <- P_i 最简单，单 peer
    P_TP > D_TP 一个 D rank 从多个 P ranks gather D 入向带宽、多个 RDMA事务、straggler
    P_TP < D_TP 多个 D ranks 从一个 P rank 读取不同 head slice P 出向带宽、fan-out、源 GPU/NIC 热点
    MLA D rank 从任意一个完整副本读取 总流量随 D_TP 复制，源 rank 选择决定热点

    例如普通 GQA、K=8：

    P8 -> D2:
D0 <- P0,P1,P2,P3
D1 <- P4,P5,P6,P7

P2 -> D8:
D0..D3 <- P0 的四个 head slices
D4..D7 <- P1 的四个 head slices

    NIXL 的映射和 GQA 重复 head 去重逻辑在 tp_mapping.py。

    MLA 的特殊热点¶

    假设 P_TP=8, D_TP=1：

    • 网络只需传一个 MLA 副本，这是好事；
    • 但当前 NIXL 映射固定让 D0 读取 P0；
    • Mooncake replicated producer 路径同样只选择一个 P rank；
    • 如果每 GPU 对应不同 NIC/rail，会形成 P0 热点。

    MoRIIO 针对 D_TP=1 + MLA + P_TP>1 单独实现了跨请求 round-robin，在 P ranks 间分摊流量，见 moriio_connector.py。

    但 MoRIIO 的通用异构 TP 能力较弱：普通 attention 只有当 P、D 两侧都已经进入 KV-head 复制区，即

    min(P_TP, D_TP) >= K

    才允许异构 TP；否则直接 NotImplementedError，见 moriio_connector.py。

    6. 网络字节量¶

    不考虑 padding、量化和 DCP，普通 attention 每个请求在所有 D ranks 上需要接收：

    Bytes_normal
≈ transferred_tokens
 × L
 × max(K, D_TP)
 × (Dk + Dv)
 × e

    只要 D_TP <= K，改变 TP 不改变集群总传输字节数，只改变每个 rank 的份额和 peer 拓扑。

    MLA：

    Bytes_MLA
≈ transferred_tokens × L × D_TP × latent_dim × e

    即网络总量直接与 D_TP 成正比。

    数值例子¶

    普通 80 层 GQA，K=8, Dk=Dv=128, BF16：

    每 token = 80 × 8 × 256 × 2 = 320 KiB
4096 tokens ≈ 1.25 GiB

    单个 400 Gb/s 链路理想下限约 27 ms，按 75% 有效带宽约 36 ms。

    DeepSeek-V3 MLA，按 61 layers × 576 dims × BF16：

    每 D rank、8192 tokens ≈ 549 MiB
D_TP=1：总线量约 549 MiB
D_TP=8：总线量约 4.29 GiB

    因此 MLA decode 若使用大 TP，很容易让 P/D 链路成为 TTFT 主项；P8 -> D1 在网络上通常远优于 P1 -> D8。

    7. 当前代码中最可能的实际瓶颈¶

    ① Descriptor/posting，而非链路带宽¶

    NIXL 为每个 region、每个 block 建 descriptor。普通 attention 通常一个 layer 是一个 region，所以每 rank 每请求大约：

    Ndesc ≈ L × ceil(tokens / block_size)

    例如：

    80 layers × 8192/16 blocks = 40,960 descriptors

    这时即使 NIC 没跑满，CPU 构造 descriptor、提交 WR、doorbell 和 CQ 处理也可能先饱和。

    Mooncake只有在源/目标都是完整 block、offset 为零且 block IDs 同时连续时才合并 descriptor；异构 TP 的 head slice 长度小于完整 block，因此通常无法合并，见 mooncake_connector.py。

    ② 较小 TP 一侧聚合¶

    • P_TP > D_TP：D rank 多源 gather，D GPU/NIC 入向成为热点。
    • P_TP < D_TP：P rank 一对多 fan-out，P GPU/NIC 出向成为热点。
    • 如果整机只有一张共享 NIC，TP 重排不能增加节点总带宽，只会增加连接和 descriptor 数。

    ③ 全 rank 完成屏障¶

    单个 rank 走错 NIC、PCIe 跨 NUMA、发生重传或 CQ 堵塞，就会拖住整个请求。平均带宽正常但 P90/P99 TTFT 很差时，应首先比较各 TP rank 的完成时间。

    ④ Host staging¶

    NIXL host-buffer 路径还要执行 GPU→Host、网络、Host→GPU；接收后的 H2D 是按 group 同步复制，代码中也留下了尚未 coalesce 的 TODO，见 base_worker.py。跨节点 GPU 部署应优先确认 GPUDirect RDMA 生效。

    ⑤ MoRIIO 逐层 READ/SQ 深度¶

    MoRIIO READ 当前逐 layer 调用，并注明尚未支持 multi-session batch read；SQ full 时会退避重试，见 moriio_connector.py。这类瓶颈表现为 NIC 利用率不高，但提交延迟、SQ-full 日志和尾延迟很高。

    8. 建议的定位顺序¶

    NIXL 已直接暴露：

    • vllm:nixl_xfer_time_seconds
    • vllm:nixl_post_time_seconds
    • vllm:nixl_bytes_transferred
    • vllm:nixl_num_descriptors
    • vllm:nixl_num_kv_expired_reqs

    定义见 nixl/stats.py。

    判定方法：

    现象 瓶颈
    post_time 高，随 descriptor 数线性增长，NIC 不满 descriptor/CPU posting
    post_time 低，xfer_time ≈ bytes / link_bw，NIC 满 网络带宽
    xfer_time 高但 NIC 低 GPUDirect 未生效、PCIe/NUMA/错误 rail
    少数 rank 明显慢 TP 映射热点、GPU–NIC 亲和性
    kv_expired_reqs 增长 D 排队、握手或网络时间超过 P lease
    MLA 的 P0 满、其他 P ranks 空 固定 replica source 热点
    MoRIIO 出现 SQ full QP/SQ/WR 提交能力不足

    部署建议¶

    • 普通 MHA/GQA 异构 TP：P、D 两端统一使用 LBHNC，避免 LBNHC 上的 GPU permute。
    • 优先保持相同 block size；异构 block size 与 head-sharding 同时出现时，NIXL 有明确限制。
    • 不要仅因为 BLHNC 物理跨层连续就假设 descriptor 已合并；应以 nixl_num_descriptors 实测。
    • 普通 attention 尽量让 P/D 较小 TP 一侧拥有足够 NIC 带宽，或采用多 rail、GPU–NIC 亲和绑定。
    • MLA 优先减小 D_TP；P_TP>D_TP 可减少总线量，但必须把请求分散到不同 P replica source。
    • 若 post_time 是主要项，可尝试更大 block size，权衡 prefix-cache 粒度和尾块浪费。
    • 跨节点优先 GPU-direct buffer；避免 host staging。
    • MoRIIO 普通 head-sharded 异构 TP 当前不合适；NIXL/Mooncake 能力更完整。
